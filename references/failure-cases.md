# 纠纷反例库

每个反例都是一条可复用的**歧义模式**。翻译时若检测到用户原话匹配某条模式，直接触发对应追问。

---

## 一、真实判例（有法律后果）

### 案例1 · 齐齐哈尔富拉尔基区法院（2025）

**事实**：顾客要求「剪短点、薄点，修个造型」。理发师问「多短」，顾客答「能扎，能扎上，就正常能扎到这」。理发师追问「底下头发还要不要」，答「不要了」，理发师一次性剪下 60cm 长发。顾客发现后索赔 5万元精神抚慰金。

**判决**：理发师未明确顾客关于头发所剪长短的具体要求，酌定赔偿 1000 元。

**歧义模式**：
- 「能扎上」→ 用功能反推长度，顾客心中有参照（手能握住、能绕圈），但从未说出具体厘米数
- 关键缺失：**「扎」的目标位置从未被确认**（马尾？发圈？盘发？）
- 失效环节：理发师追问了一句「底下要不要」，得到的是位置确认而非长度确认，被误当成全面授权

**Skill 应对**：识别到「能扎/ 能绑 / 能盘」等功能性表述时，必须追问：
> 「能扎」的参照是：Ａ 能握拳抓住的长度 ／ Ｂ 手腕绕两圈的长度 ／ Ｃ 细发圈能固定住的最小长度？

### 案例 2 · 广州白云区法院

**事实**：唐女士因婚礼造型需要，长发及腰，前去修剪。修剪后明显短于要求，双方争议。报警未果后起诉，索赔修复费 3000 元、精神抚慰金 3000 元等。

**判决**：美发店赔偿损失 500 元，退还会员卡充值 900 元。

**歧义模式**：
- **场景驱动的长度**（婚礼造型）与日常长度混淆，顾客自身也没想清楚
- 缺失「婚礼造型」的具体要求（盘发/ 编发/ 保持长度？）
- 失效环节：场景成为隐含需求，但从未转化为可执行指令

**Skill 应对**：识别到场景化需求（婚礼/ 面试/ 拍照/ 毕业）时，必须追问该场景下的具体发型要求，不能只按当前长度推演。

### 案例 3 · 珠海横琴粤澳深度合作区消协调解（2026）

**事实**：消费者陈女士用粤语沟通，表达「仅需简单修剪，无需剪得太短」。理发师不熟悉粤语，且修剪过程中长时间位于消费者身后操作。双方未能持续确认修剪长度。消协调解，商家赔偿 500 元。

**歧义模式**：
- **「简单修剪」+ 对方未听懂 + 缺乏过程确认** 三重叠加
- 关键缺失：全程没有长度基线
- 失效环节：视觉盲区（理发师在身后）+ 语言不通 + 无镜子确认

**Skill 应对**：
- 输出指令卡时，对关键长度要求加**可视觉核验的锚点**（「剪到耳上，镜子里能看到耳朵上缘」）
- 提醒用户在剪到一半时要求确认

## 二、语义歧义模式库（可复用）

### 模式 A · 「一点」的无量词陷阱

| 用户可能说 | 实际含义 |
|---|---|
| 「修一点就行」 | 只剪分叉，长度尽量不变 |
| 「剪短一点」 | 从 30cm 剪到 25cm？还是 10cm？ |
| 「两边弄短点」 | 贴头皮推一遍？留一层扎手的短茬？还是只用剪刀修薄？ |

**根因**：「一点」在双方心中刻度不同。理发师眼里的 3cm 可能真的「不算多」，但对留长发的顾客等于几个月等待。

**Skill 应对**：任何模糊量词必须换成**位置锚点或可验证结果**，且给 2-3 个区间选项让用户选。

注意数字的归属：**位置型数字进问句**（剪到耳上、留到锁骨），**卡尺型数字不进问句**（3mm／5mm 是推完留下的长度，顾客既没刻度、又常听成「剪掉这么多」）。用「几乎看到头皮／一层扎手的短茬／能看出一层头发」替代。完整对照见 `glossary-cutting.md` 的「双参照系」。

### 模式 B · 视觉长度 ≠ 实际长度

**事实**：即使最长处只少 2-3cm，视觉上仍可能明显变短。原因：

- 剪了明显层次后，上部头发变短，厚重下垂感减轻，**整体轮廓上移**
- 自然卷、沙发发质、烫过的头发**吹干后回缩**
- 顾客看的是视觉效果，理发师说的是实际长度，**双方都没说错**

**Skill 应对**：用户表达「明明没剪多少但看起来短了」的困惑时，解释轮廓上移与回缩机制，并在首次剪发时明确层次方案。

### 模式 C · 形容词的双向失效

| 用户说 | 理发师常理解 | 用户实际想表达 |
|---|---|---|
| 「稍微修一下」 | 修掉所有受损发尾 | 长度千万别变 |
| 「层次感强一点」 | 打薄去量 | 顶部留长做造型 |
| 「显得精神」 | 剪短露额 | 三七分+顶部留长 |
| 「不要那么塌」 | 剪短 | 高层次增加发根支撑，或两侧推剪 |

**根因**：形容词没有对应的唯一操作。「精神」在长度、层次、两侧轮廓三个维度上都有对应方案，效果完全不同。

**Skill 应对**：形容词必须落到**具体维度 + 具体操作 + 具体数值**。

关键约束：选项必须是**同一件事的不同改法**，不是三个不同的发型。「显精神」的正确拆法是问「你想靠哪个部位显精神」；错误的拆法是给出「短碎发 / 寸头 / 大背头」——那是造型推荐，用户挑哪个都是在选发型，不是在选自己的需求。

选项措辞用「你想**靠哪个部位**达到……」，不用「我**建议**你……」。前者把决定权交回用户，后者是模型替用户做主。

### 模式 D · 长度约束与造型需求的冲突

**典型**：「我想留长发但想显精神」——长发必然削弱精神感（露额、线条利落）。

**Skill 应对**：识别到此类冲突时，**明确指出冲突**，然后把选择权交回用户：

> 你这两条有点冲突：长发会削弱精神感（精神感主要靠露额和利落线条）。
> Ａ 优先留长——靠层次和蓬松度补救，接受精神感弱一些
> Ｂ 优先精神——长度必须减，配高层次撑头顶
> Ｃ 各让一步——留到锁骨，露额 + 高层次

不要假装两个需求能同时满足，也不要自己选一个折中方案替他定。折中方案可以作为 Ｃ 选项出现，但必须和 Ａ Ｂ 并列，让用户自己挑优先级。

### 模式 E · 物理盲区型失误

**事实**：剪刘海和后脑层次时，顾客在镜子里**看不到理发师正在做的事**。

**Skill 应对**：刘海与后脑区域的指令卡必须包含**过程确认节点**（「剪刘海时我会抬眼确认长度」），而不是只在最后看效果。

### 模式 F · 术语的流派差异

「高层次」「内扣」「平头」在不同城市、不同师徒体系下含义存在差异。同一术语可能是店内沟通的「黑话」。

**Skill 应对**：术语 + 物理锚点双输出。锚点必须**理发师可执行**：
- ✓「从下往上推剪，过渡带在耳朵上缘」
- ✗「看起来自然一点」

### 模式 G · 效果描述被误读为剪法指令（防越界）

**典型**：用户说「想显脸小」「头发太塌了想蓬松」「显得温柔一点」，模型直接输出「露额 + 两侧收窄 + 高层次」。

**根因**：用户说的是**效果**，不是**改哪儿**。效果到剪法的映射不唯一，模型一旦自己完成这个映射，就从翻译器变成了造型师——用户交出去的是自己的审美决定权。

**Skill 应对**：效果类描述必须先追问「你想靠**哪个部位**达到这个效果」，让用户指定改动位置。

| 用户说 | ✅ 正确追问 | ❌ 越界 |
|---|---|---|
| 想显脸小 | 靠两侧收窄？靠露额？还是靠发尾贴脸？ | 直接给「露额 + 两侧收窄」 |
| 头发太塌想蓬松 | 靠头顶撑起来（层次），还是靠两侧剪短变利落？ | 直接给「高层次 + 高渐变」 |
| 显得温柔一点 | 想靠刘海柔和感，还是靠发尾内扣？ | 直接给「中长发 + 空气刘海 + 内扣」 |

**判据**：追问的选项必须都指向**同一件事的不同改法**，不是三个不同的发型名。选项里出现「短碎发」「碎盖头」「狼尾」这类**发型名**，说明已经在做推荐了。

### 模式 H · 语义等价 ≠ 可以代填（两步推理禁令）

模式 G 管的是「效果描述直接给方案」。这条管它的变种：模型不直接给方案，而是走两步——

> 用户说「想蓬松」→ 蓬松对应「高层次」→ 卡片写「高层次」

中间那一步在模型脑子里完成，用户没看见，但结果和模式 G 一模一样：**用户交出去的决定权，被模型的推理链悄悄接管了。**

**禁令**：不允许用「效果 → 术语」的两步推理产出卡片里的任何一行。效果必须先**回到用户嘴里**（在追问选项里点选过），才能进卡片。

**五档判定**：

| 用户原话 | 卡片写 T | 判定 | 理由 |
|---|---|---|---|
| 说了 T 或其口语别名（「打薄一点」→ 打薄） | 打薄 | ✅ 合法 | 直接引用 |
| 说了维度 + 方向（「两边弄短」→ 渐变） | 渐变 | ✅ 合法 | 维度方向都给了，术语是标准命名 |
| 说了维度、没说类型（「修一下发尾」→ 内扣） | 内扣 | ❌ 越界 | 方向是模型选的 |
| 只说了效果（「想显脸小」→ 露额 + 两侧收窄） | 露额 | ❌ 越界 | 两步推理 |
| 只说了效果，但在追问里选了「两侧收窄」 | 两侧收窄 | ✅ 合法 | 有显式确认，可引用 |

**一句话判据**：这一行能不能回答「用户在哪句话里选过它？」——答案必须是**引用**，不能是**推断**。

**自检话术**（出卡前逐行问自己）：
- 「这一行是用户的哪句话？」→ 能指出原话或选项，留
- 「用户没直说，但意思差不多」→ 标 `[待确认]`，不进卡片
- 「用户显然会想要」→ 删掉。「显然」就是两步推理的入口

**为什么这比模式 G 更隐蔽**：模式 G 的错误看得见（说了「推荐」「建议」），模式 H 的错误看不见——卡片上写着用户自己的需求词，只是把它翻译成了用户没选过的术语。用户会以为「对对就是这个」，实际上那个「这个」是模型挑的。

## 三、追问模板库

翻译过程中命中上述模式时，从此处取追问话术。**每个问题必须带 2-3 个数字化选项**，降低回答成本。

**选项纪律**：选项是「同一件事的不同改法」，不是「三个不同发型」。给的是部位与改法，不是发型名。

### 关于长度
```
你说的「短一点」，大概是：
Ａ 剪到耳朵上缘（约 6cm），还能盖住耳朵
Ｂ 剪到耳垂（约 10cm）
Ｃ 剪到后颈发际线（约 3cm），耳朵完全露出
```

### 关于「修一下」
```
「修一下」有两种做法：
Ａ 只剪分叉/受损部分，长度基本不变
Ｂ 整体剪短一个明显长度
你偏向哪个？
```

### 关于「显得精神」
```
「精神」你想靠哪儿？
Ａ 靠两侧——推剪+ 露出额头，线条干净利落
Ｂ 靠头顶——顶部留长 + 层次，撑起来有蓬松感
Ｃ 靠整体——统一剪短一个明显长度
```
（不给「短碎发」「寸头」这类发型名——那是在替用户选造型）

### 关于「想显脸小」
```
「显脸小」靠哪个部位？
Ａ 两侧收窄——修掉鬓角和耳侧堆积
Ｂ 露额——把额头露出来，脸型轮廓更清楚
Ｃ 发尾贴脸——内扣往里收，视觉上把脸框住
```

### 关于发质约束（必须提示而非替换）
```
你发质偏细软 / 发量偏少，
低层次厚重剪法会贴头皮——这个方向物理上做不出蓬松感。
你刚才选的是低层次，要换高层次吗？还是保持低层次接受贴头皮？
```
（**不写「建议改中高层次」**。提示不可行 + 把决定权交回用户，不代替用户改方案）

### 关于底线确认（输出卡片时必须包含）
```
⚠️ 这几条我需要明确：
· 两侧不可再推剪
· 发尾最多剪 2cm
· 刘海可以短，但不能盖不住眉毛
```

## 四、判例检索说明

处理用户模糊原话时：

1. 检查是否命中「语义歧义模式库」A-H 任一条（G 是效果越界、H 是**两步推理代填**，两条命中都强制追问部位或标 `[待确认]`）
2. 若命中，从「追问模板库」取对应话术，**并用掉当轮追问预算**（整轮最多两轮，见 SKILL.md）
3. 若用户原话接近判例事实（功能性长度表述、场景化需求等），参照对应案例的 Skill 应对
4. 无论是否命中，输出指令卡时强制执行硬底线规则
5. **出卡前过溯源闸门**：逐行检查能否回指到用户说过的话，回指不到的删掉或标 `[待确认]`；回指方式必须是**引用**，不能是「推断」
6. 用户问「我适合什么发型」→ 声明不做造型推荐，转为追问用户自己想改变什么
7. 用户说「你看着办」「都行」→ 这一项可给默认值，但必须在卡片旁标出来源，供用户否决（授权默认 ≠ 静默默认）
