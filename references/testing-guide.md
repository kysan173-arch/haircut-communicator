# 测试手册

## 为什么需要三层测试

单层测试都是自欺：

- 只测结构 → 文件都在，但词典查不到用户说的话，照样跑偏
- 只测词典覆盖 → 词典齐全，但流程该追问的不追问，照样出废卡
- 只读文档自省 → 「我觉得挺顺」，这是最危险的

三层各管一件事，**缺一层就是自欺**：

| 层 | 测什么 | 谁判 | 自动化 |
|---|---|---|---|
| L1 静态 | 结构完整性、范围边界、规则存在性 | 脚本 | ✅ |
| L2 词典覆盖 | 测试原话能否在词典中检索到映射 | 脚本 | ✅ |
| L3 行为 | 真实翻译是否消除歧义 | 人/LLM | ❌ 必须人工 |

**L2 的价值被低估了。** 用户在理发店说的几乎不会是术语——如果一条真实原话在词典的「口语别名」列检索不到，L3 翻译必然跑偏，而这是**可在跑 L3 之前就判定**的失败。L2 提前抓出 L3 的大部分失败。

---

## 一键运行

```bash
# L1 静态检查
python scripts/check_static.py

# L2 词典覆盖
python scripts/check_lexicon_coverage.py

# L3 行为用例与判定清单
python scripts/run_behavior_test.py

# 查看单个 L3 用例
python scripts/run_behavior_test.py --case 5
```

退出码：0 = 通过，1 = 有失败项。可直接接入 CI 或 pre-commit。

## L1 静态检查

**测什么**：148 个二值判定项，分十一组。

| 组 | 检查内容 |
|---|---|
| 结构 | 必需文件存在、烫染词典已移除 |
| 元数据 | frontmatter 完整、description 含剪发声明与烫染排除声明 |
| 范围 | 主流程文件不得残留烫染术语（边界声明句自动豁免） |
| 流水线 | 四段流水线、硬底线规则、六维模型齐全 |
| 指令卡 | 长度/层次/打薄区块、硬底线区块、正反示例 |
| 输入模板 | 四类字段、双版本、脸型不收的说明 |
| **溯源闸门** | 溯源章节存在、审美默认值已删除、发质表不再用「推荐」列、模式 G 存在 |
| **后颈与约束** | 后颈收边三种形状齐全、收边高度必须量化、【整体约束】独立区块、声明不是第七维 |
| **追问与推理** | 追问预算两轮封顶、第3轮明禁、授权默认可区分；模式 H 存在、判据为「引用非推断」；长发三锚点齐全 |
| **追问用语** | 追问用语规则存在、mm 禁入问句、状态 A 同步受约束、词典「双参照系」表存在、1cm 换算不回退、反例库无坏模板；参照尺三系（手部/社会符号/现状对比）、结果优先、捏发兜底、单次最多两种参照 |
| **照片输入** | 照片章节存在、验证器定位、不可做什么清单、三条触发条件、日常不索取照片、只要必要视角、读图用位置、照片结果必须回确认；词典含位置词口径表与视角表；指令卡含照片坐标且声明「精确≠授权」 |

**跑它能抓什么**：改文档时不小心删了硬底线规则、范围收窄漏改了某个文件、模板字段被移除、**默认值重新混进指令卡**。

## 溯源专项（L1 第七组 / L3 判定项）

这一组专治**Skill 从翻译器退化成造型师**。

L1 能机检的部分：

| 检查 | 为什么必须机检 |
|---|---|
| SKILL.md 含「溯源闸门」章节 | 规则存在性，纯文本判定 |
| 指令卡不含「可默认高层次/空气刘海/内扣」 | 默认值是最隐蔽的越界，文档里删了才能防回流 |
| 发质表列名不是「推荐 \| 禁忌」 | 「推荐」二字本身就是设计动作 |
| 反例库含模式 G | 效果被误读为剪法指令的防护条目 |

**机检抓不到的**（只能靠 L3 人判）：

- 模型是否在追问里偷偷塞了发型名（短碎发/寸头/狼尾）
- 卡片上是否出现了语义等价但用户没提过的项（「用户说蓬松，模型输出高层次」——高层次算不算越界？取决于用户是在追问里选的，还是模型自己推的）

**判定原则**：卡片的每一行都要能回答「这句话用户说过吗」。L3 判定时逐行追问，答不上来就是越界。

## 追问预算专项（L1 第九组 / L3 用例 18-19）

溯源闸门要求追问，但**追问会退化**：连问三轮、每轮三问，用户直接放弃。所以追问本身也要有上限，且这个上限必须是硬约束，不能只写「尽量简洁」——「尽量」等于没有。

| 检查 | 值 |
|---|---|
| 整轮追问上限 | 2 轮 |
| 第 1 轮 | ≤3 个问题，按「长度 → 两侧 → 发质 → 部位」优先级 |
| 第 2 轮 | ≤1 个问题，只问仍然阻塞出卡的那一项 |
| 第 3 轮 | 禁止 |
| 超预算后 | 出卡 + 未定项标 `[待确认]` + 后果提示 |

**关键区分：授权默认 ≠ 静默默认。** 用户说「你看着办」时模型**可以**给值（这是用户交权，溯源成立），但必须在卡片旁标出来源并留否决权。区别就在那一句标注上——没有它，就跟第三轮明令禁止的「模型替用户定」是同一件事。

**为什么这条要进 L1 机检**：规则一旦只在文档里写「注意不要问太多」，实际执行时模型会为了「信息齐全」而无限追问。把「≤3」「≤1」「第 3 轮禁止」写成可机检的字符串，改文档时漏改一处就报红。

## 两步推理专项（模式 H / L3 用例 20）

模式 G 抓的是「效果直接给方案」，看得见。模式 H 抓的是它的隐身版本：

> 用户说「想蓬松」→（模型脑内）蓬松对应高层次 → 卡片写「高层次」

中间一步在模型脑子里完成，用户看不见，但结果一样是代填。判定只有一句：

**这一行能不能回答「用户在哪句话里选过它」——答案必须是引用，不能是推断。**

| 用户原话类型 | 卡片可写 | 判定 |
|---|---|---|
| 说了术语或其别名 | 该术语 | ✅ 引用 |
| 说了维度 + 方向 | 该方向的标准术语 | ✅ 引用 |
| 说了维度没给类型 | 不得写该维度的具体类型 | ❌ 越界 |
| 只给效果 | 不得写具体术语 | ❌ 越界 |
| 只给效果，但追问中用户选了 | 用户选的那项 | ✅ 引用（有显式确认） |

**自检入口**：当你想说「用户显然会想要」时，那个「显然」就是两步推理的入口。

## 追问用语专项（L1 第十组 / L3 用例 22-23）

这一组专治**追问问了一个顾客答不上来的问题**。

**两类失败，机制不同**：

| 失败 | 例子 | 为什么错 |
|---|---|---|
| 卡尺数字进问句 | 「两侧推 3mm 还是 5mm？」 | mm 是**推完留在头上的长度**，不是剪除量。顾客没毫米刻度，还会理解成「剪掉 3mm」——他以为很保守，实际是贴头皮推一遍 |
| 裸术语进问句 | 「要高层次还是零层次？」 | 顾客不知道层次是什么，答案只能是瞎猜。猜完的选项，执行时照样走样 |

**根因**：第 2 段只要求「追问必须带数字」，第 3 段的「目标效果（用户听得懂）」只约束指令卡，不约束追问。于是模型学会了「带数字」，没学会「数字要说人话」。

**L1 机检什么**：

| 检查 | 为什么必须机检 |
|---|---|
| SKILL.md 含「追问用语规则」 | 规则存在性 |
| 明确「毫米数不进问句」 | 这是最容易被模型漏掉的一条，缺了就回退 |
| 状态 A 输出规则同步含禁令 | 只写在第 2 段不够——输出阶段才是真正生成问句的地方 |
| 词典含「双参照系」表 | 没有替代表达，禁令只是「不许说」，模型会换成另一个术语 |
| `1cm ≠ 3mm` 不回退 | 历史 bug：1cm 曾被写成约 3mm（实为约 3 分），差 3 倍，直接导致长度全线走样 |
| 反例库无「推剪到 3mm」 | 引用文件是模型最容易照抄的句子来源 |

**L3 判定**（用例 22、23）：追问全文不得出现 `mm／毫米／圆寸／板寸／卡尺`；每个选项必须能对着镜子看或用手摸；裸术语判失败。

### 直观化的四个参照系（用例 24）

「直观」的唯一判据：**用户需不需要在脑子里做转换**。需要转换的都不直观。

| 参照系 | 适合 | 为什么直观 | 反例 |
|---|---|---|---|
| **结果** | 全场景，优先用 | 不用想长度，只想功能 | 「剪多长？」 |
| 位置 | 中长发 | 对着镜子能验证 | — |
| 手部度量 | 1-20cm 的短距离 | 抬手就能比 | 「5cm」 |
| 社会符号 | 短发 | 一听就有画面 | 「圆寸 3mm」 |
| 现状对比 | 长发 | 低头就能看见 | 「剪掉 10cm」 |
| 捏发确认 | 用户全程说不清 | 手指停的位置就是底线 | 「您再想想？」 |

两条约束：**先定结果再定位置**（结果可想象，长度不可想象）；**单次追问最多两种参照**（三种全上等于把选择题变问答题）。

**变异测试已做**：把换算改回「约 3mm」、把反例改回「推剪到 3mm」，L1 精确报红 2 项。

## 照片专项（L1 第十一组 / L3 用例 25-27）

照片是**唯一能推翻本 Skill 定位的输入**。一旦允许「看图给建议」，第三轮刚拆掉的推荐引擎会立刻回来——而且这次带着照片当背书，用户更难察觉。

**边界一句话**：照片是**验证器**（他说的和实际是不是一回事），不是**推荐器**（他适合什么）。

| 照片可以 | 照片绝对不可以 |
|---|---|
| 读现状（发长落点、后脑形状、层次、两侧状态） | 判断脸型、五官、发质好坏 |
| 校验用户描述与事实的偏差 | 推荐发型、评价好不好看 |
| 给指令卡补精确坐标 | 凭照片直接决定剪法 |

**成本控制是这组的第二条主线**。拍四张照片对用户是负担，所以设三条触发：改后脑／长发大改／追问两轮说不清。日常「两边修短」要照片，属于体验倒退——和「不默认甩模板」同理：**只有会改变结果的输入才值得收。**

**为什么后面那张单独说**：其余三面照镜子就能看见，后脑是真正的 180° 盲区，也是颈线争议的发生地。四面照片的价值不对称——一面顶三面。

**L1 机检什么**：章节存在、验证器定位、不可做什么清单、三条触发条件、「不要照片」条款、「只要必要的那一张」、读图用位置、照片结果必须回确认；词典的位置词口径表与视角表；指令卡的「照片坐标」与「精确≠授权」。

**L3 判定**（25-27）：从照片推方案即失败；凭照片判断脸型发质即失败；日常场景索取多角度照片即失败；照片看到的问题未经用户确认就写进卡即失败（与「两步推理代填」同类，只是中间那步换成模型的眼睛）。

## L2 词典覆盖

**测什么**：39 条真实原话（19 条正样本 + 20 条负样本），验证原话能否**行级**反查到正确术语。
另含**长度锚点资源检查**：9 个锚点（耳上/耳垂/下颌线/眉上/锁骨/肩线/胸线/腰线/后颈发际线）必须齐全——追问话术和长发场景都靠这张表落地。

**判定标准（v2，2026-10-19 重写）**：

1. **只在「口语别名」列反查**。效果列 / 特征列 / 适配脸型列一律不参与匹配——这是 glossary「使用纪律」的机检落地。
2. **正样本**（用户说了维度+类型）：命中必须是期望术语那一行。
3. **负样本**（只说效果 / 只说维度没说类型 / 只是发质信息）：**必须零命中**，命中任何术语行即判越界。
4. **判据自检**：脚本先跑 3 组「故意给错期望」的反向用例，全部判红才继续。判据恒真时直接退出——先证明尺子准，再量人。

**为什么加了负样本**：只有正样本的测试集**会奖励越界**。旧版把「想显脸小」的期望写成命中`渐变`、「头发太塌了」写成命中`高层次`，等于用测试在教模型替用户选方案。

**旧版为什么是假绿灯**（v1，已废弃）：

```python
hit = [kw for kw in expect_keywords if kw in glossary]   # 全文子串包含
```

只要关键词在 166 行词典里出现过一次就永远通过。实测误命中四例：`想显脸小→渐变`、`别太老气→刘海`、`显得温柔→空气刘海/内扣`、`剪短点薄点能扎上就行→层次`。**31/31 不携带任何信息量。**

**跑它能抓什么**：用户会说但词典没收的说法（真实缺口）、词典里埋着的越界诱因、判据本身的退化。

## L3 行为测试

**测什么**：27 条行为用例，实跑 Skill 后逐条勾选判定项。

### 为什么这层无法自动化

「这条指令理发师能不能看懂」不是二值判定。需要人读输出后判断。因此把判定拆成**客观可勾选项**——

- 是否触发了追问（看有没有问）
- 是否带数字（正则可查，但语义要人确认）
- 是否误引入烫染（关键词可查）
- 是否包含硬底线（关键词可查）

**能自动的尽量自动，不能自动的写清判定标准。** 这是 L3 唯一诚实的做法。

### 用例覆盖

| 类别 | 用例 |
|---|---|
| 长度模糊 | 剪短一点但别太短、修一下就行 |
| 两侧模糊 | 两边弄短点 |
| 形容词歧义 | 想显精神 |
| 修饰意图 | 头发太塌了 |
| 判例原话 | 能扎上就行、婚礼长发冲突 |
| 发质约束 | 发量少、头发硬易炸 |
| 范围边界 | 顺便烫、染棕色 |
| 组合约束 | 细软+圆脸+齐刘海 |
| **溯源越界** | 我想显脸小、头发太塌想蓬松 |
| **推荐请求** | 我适合什么发型 |
| **整体约束** | 就稍微修一下就行 |
| **后颈收边** | 后面修圆满一点，两边修到耳朵上方 |
| **追问预算** | 显得精神一点（两轮都说不清）、头发太塌了→「你看着办」 |
| **两步推理** | 想显脸小→用户选Ａ两侧收窄 |
| **长发修剪** | 到腰的长发剪到肩下、一刀切、别打层次 |
| **追问用语** | 两边弄短点（禁 mm 卡尺）、「清爽一点」（禁裸术语） |
| **追问直观化** | 剪短点但说不上来（参照系选择与结果优先） |
| **照片·后脑核验** | 附后脑照说「后面不整齐」（只读现状，不推荐） |
| **照片·不该索取** | 「两边弄短点，要不我拍照给你」（日常场景不索取） |
| **照片·红线** | 附正面照说「脸圆想显脸小」（不判脸型、不给方案） |

### 执行流程

```
1. 激活 Skill：说「我要剪发，帮我翻译需求」
2. 逐条输入用例原话（如「剪短一点但别太短」）
3. 记录完整输出
4. 逐条对照 objective_checks 勾选
5. 失败项定位：是规则缺失（SKILL.md 没写清）还是术语缺失（词典没收录）？
```

## 真实场景盲测（L3 增强）

**自动化用例是靶场，真实需求是实战。** 靶场打得好不代表实战赢——靶场的原话是我们自己写的，天然对词典友好。

### 怎么测

找 3-5 个**不在测试集里**的真实模糊需求，来源：

- 你自己下一次要剪的头发
- 朋友/家人的理发需求
- 社交媒体上的理发吐槽帖

### 判定标准

| 维度 | 问题 |
|---|---|
| 歧义识别 | 有没有该追问的没追问？ |
| 数字量化 | 输出的长度能直接照着剪吗？ |
| 底线建立 | 有没有一条「不可越界」的声明？ |
| 可执行性 | 假设你是理发师，能照着这条卡剪出来吗？ |
| 越界 | 有没有混入烫染内容？ |
| **溯源** | 卡片每一行，用户真的说过吗？ |
| **是否在替用户选** | 追问选项里有没有偷塞发型名？ |

**特别关注盲测失败的地方**——那是词典的真实缺口，不是测试集设计不足。

---

## 回归测试

改 Skill 后必须重跑全部三层：

```
L1（结构是否破坏）
L2（词典是否仍覆盖）
L3（行为是否退化）
```

特别地：改动 SKILL.md 规则后，L1 的「规则存在性」检查和 L3 的判定项都要重新过一遍。规则措辞变了但检查项没跟着变，L1 就成了假绿灯。

## 已知测试盲区

诚实列出当前测不到的东西：

| 盲区 | 原因 | 何时补 |
